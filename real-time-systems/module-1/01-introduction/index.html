    1.1 Introduction to Real-time Systems¶

    Learning objectives¶

    After completing this chapter, you will be able to:

    • Explain what a real-time system is
    • Understand why timing is important in robotics
    • Distinguish between a correct result and a timely result
    • Identify examples of time-critical tasks in robotic systems
    • Explain why a faster computer is not necessarily a better real-time system

    1.1.1 What is a real-time system?¶

    A real-time system is a computing system designed to perform specific tasks within the specified/defined time limits (deadlines), ensuring that responses are delivered when they are needed. In such systems, producing the correct result in not enough, the result must also be available by the required time. For example, a robot's collision avoidance system must detect an obstacle and respond quickly enough to prevent a collision. Producing the correct response too late may still result in failure.

    In ordinary computing, we are often mainly interested in whether a program produces the correct output. In real-time computing, the program must also produce its output within a specified timing constraint.

    Let's consider a mobile robot approaching an obstacle. To avoid a collision, the robot must:

    1. Read information from its sensors.
    2. Determine whether an obstacle is present.
    3. Decide whether it needs to stop.
    4. Send the appropriate command to its motors.

    If the robot makes the correct decision but responds too late, it may collide with the obstacle. Therefore, producing the correct decision is not sufficient. The decision must also arrive in time.

    This illustrates an essential principle of real-time computing: both the result and its timing determine whether an operation is successful.

    Key concept

    Real-time correctness = Correct result + Correct timing

    A real-time system must satisfy both its functional requirements (what it should do) and its timing requirements (when it should do it).

    1.1.2 Why is real-time operation important in robotics?¶

    Robots continuously interact with their physical surroundings. They receive information through sensors, process that information, and perform actions using actuators. Since the physical environment continues to change while the robot is processing information, delays can affect how accurately, efficiently, or safely the robot operates.

    Examples of events requiring timely responses include:

    • mobile robot approaching an obstacle
    • robotic arm reaching its target position
    • motor rotating faster than its commanded speed
    • sensor detecting an unexpected change
    • robot receiving an emergency stop signal

    The time available to respond depends on the particular task and its operating conditions.

    Example 1: Mobile robot obstacle detection¶

    Imagine a mobile robot moving toward a wall. The robot uses a distance sensor to detect obstacles and a controller to determine whether it should stop. Suppose the controller is required to produce a stop command within 20 ms after receiving a valid obstacle-detection event.

    Situation Controller response Result
    A Correct STOP command in 8 ms Meets requirement
    B Correct STOP command in 15 ms Meets requirement
    C Correct STOP command in 35 ms Misses deadline
    D Incorrect MOVE command in 5 ms Functionally incorrect

    Situation A and B both satisfy the functional and timing requirements. In Situation C produces the correct command but does not satisfy the timing requirement. Situation D responds quickly but produces the wrong command.

    Note

    The 20 ms requirement is an illustrative software deadline. A real robot's safe stopping requirements depend on its speed, sensing range, braking capability, mechanical characteristics, and other factors.

    Example 2: Robotic arm control¶

    A robotic arm may use a controller that updates motor commands every 10 ms.

    During each control cycle, the controller:

    1. Reads the measured joint position.
    2. Compares the measured position with the desired position.
    3. Calculates the next motor command.
    4. Sends the command to the motor driver.

    If the controller is delayed, the motor command may be based on outdated information directly impacting accuracy of the arm' movement. Repeated delays or inconsistent update intervals can reduce control performance and, depending on the system, may affect stability.

    There for reliable operation(s), the controller must execute according to its defined timing requirements.

    1.1.3 Does real-time mean extremely fast?¶

    A common misunderstanding is that a real-time system must always execute as quickly as possible. This is not necessarily true. The important requirement is that the system completes its operations within the specified timing constraints.

    Consider two programs performing the same task.

    Program A

    • Usually completes in 2 ms.
    • Occasionally takes 30 ms.

    Program B

    • Consistently completes in 8 ms.
    • Never exceeds 10 ms under the tested conditions.

    Suppose the task has a deadline of 15 ms.

    Program A is usually faster, but it occasionally misses the deadline.

    Program B is slower on average, but all its observed executions meet the deadline.

    For this particular requirement, Program B demonstrates better timing behavior.

    However, testing alone does not guarantee that Program B will always meet its deadline under every possible operating condition.

    Remember

    Real-time does not mean fastest. It means meeting timing requirements predictably.

    A system that is very fast but frequently misses its deadlines may be unsuitable for a time-critical applications.

    1.1.4 Real-time systems and ordinary computer programs¶

    Consider a program that calculates the average of 1000 numbers. If the program takes 100 ms instead of 50 ms, the result is still mathematically correct. For many applications, this delay may be acceptable.

    Now consider a robot controller that must update a motor command every 10 ms. If the controller occasionally takes 100 ms, the delay could significantly affect the robot's operation.

    The main difference is that the robotic controller has explicit timing requirements that must be considered alongside its functional behaviour.

    Ordinary application Real-time application
    Primarilyconcerned with producing the correct output/result Requires correct output within specified timing constraints
    Some delays maybe acceptable Delays may violate system requirements
    Execution time may be relatively flexible Timing constraints must be satisfied
    Example: generating a report Example: updating a motor controller

    Note

    The distinction isn't absolute! Ordinary applications can also have timing requirements, and not every robotic software function is strictly time-critical.

    For example, generating a robot's daily activity report may not require strict real-time execution.

    1.1.5 Where do we find real-time systems?¶

    Real-time computing is used in many applications where software must respond to events or complete operations within defined time limits.

    Robotics¶

    • Motor/position control
    • Joint position control
    • Obstacle detection & avoidance
    • Motion stabilisation

    Automotive systems¶

    • Engine control
    • ABS systems (Anti-lock braking systems)
    • ESC (Electronic stability control)

    Industrial automation¶

    • Conveyor control
    • Industrial robot controllers
    • Automated production machinery

    Aerospace systems¶

    • Flight control
    • Navigation & stabilisation
    • Aircraft control systems

    The timing requirements of these applications can differ significantly.

    Some tasks may need to execute every few milliseconds, while others may have deadlines measured in microseconds or seconds.

    There is no single universal deadline that defines all real-time systems. What matters is whether the system meets the timing requirements of its particular application.

    1.1.6 What happens when a deadline is missed?¶

    A deadline is the latest permitted completion time for a task, measured relative to a defined reference event.

    For example, if a task is released at time 0 ms and has a relative deadline of 20 ms, it must be completed by time 20 ms. If it completes at 12 ms, it meets the deadline. If it completes at 25 ms, it misses the deadline by 5 ms. A missed deadline does not necessarily mean that the system will immediately fail. Its consequences depend on what the task was and its application.

    For example:

    • A delayed display update may only be inconvenient.
    • A delayed robot status message may be tolerable.
    • A delayed motor-control update may reduce performance.
    • A delayed safety-critical response may create a dangerous situation.

    Later in this module, we will exam three important categories of real-time systems: hard, firm, and soft real-time systems, which describe different consequences of missing deadlines.

    1.1.7 Real-time systems in this course¶

    In this course, you will learn to design and evaluate software that performs operations according to timing requirements.

    You will work with examples involving:

    • Periodic sensor readings
    • Concurrent software tasks
    • Task scheduling
    • Data sharing between tasks
    • Synchronisation mechanisms

    • Measuring execution time & timing variation

    • A normal PC (Windows, Linux or macOS) with C++17. The early labs use the PC to measure execution times, observe scheduling behaviour and investigate how a general-purpose operating system affects timing. No extra hardware is needed.

    • An ESP32 microcontroller board running FreeRTOS, programmed in C with ESP-IDF. Later labs use the board to run periodic and event-driven tasks that interact with real hardware, where timing must be predictable. The ESP32 has two processor cores, and you will learn to decide which core each task runs on (Section 1.5).

    Important

    A normal Windows or Linux computer does not automatically guarantee hard real-time execution. However, it provides a useful environment for learning how to measure execution times, observe scheduling behaviour, and investigate the effects of concurrent tasks. Comparing the timing you measure on the PC with the timing you measure on the microcontroller is one of the aims of this course.

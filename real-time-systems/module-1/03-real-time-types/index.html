    1.3 Hard, Firm, & Soft Real-time Systems¶

    1.3.1 Why do we classify real-time systems?¶

    In Chapter 1, we studied that a real-time system must produce correct results within specified timing constraints.

    However, not every missed deadline has the same consequences.

    Consider three situations:

    1. A safety-critical robot controller fails to respond within its required deadline.
    2. A robot's object-detection system produces a result too late for the current control decision.
    3. A robot's monitoring dashboard displays an update slightly later than expected.

    All three situations involve timing delays, but their consequences are different.

    In the first case, a missed deadline may violate a critical system requirement.

    In the second case, the late result may no longer be useful.

    In the third case, the information may still be useful despite the delay.

    Real-time requirements are commonly classified into three categories:

    • Hard real-time
    • Firm real-time
    • Soft real-time

    The classification depends primarily on the consequences of missing a deadline, not on how short the deadline is (Read more: Real-Time & Embedded Systems, Purdue University).

    1.3.2 Hard real-time systems¶

    A hard real-time requirement is one in which missing a deadline is considered a system failure. Every required deadline must be met for the system to satisfy its timing specification (Read more: Difference between hard & soft RTS - Geeksforgeeks).

    In safety-critical applications, violating such a requirement may have serious consequences, such as injuries or more. For example, an air traffic control or surgical robotic arm.

    Example: Safety-critical robot stopping function¶

    Consider an industrial robot operating near a hazardous area.

    Suppose a safety-related controller has a validated requirement to generate a particular stop-related output within a specified time after receiving a safety input.

    If the output is produced too late, the system violates its timing requirement.

    Even if the output is logically correct, it does not satisfy the hard real-time specification.

    Key concept

    In hard real-time systems, missing a required deadline is unacceptable.

    A correct result delivered too late does not satisfy the system's timing requirements.

    Characteristics¶

    • Guaranteed response time: Deadlines must be met under the specified operating conditions.
    • Worst-case timing behaviour is important.
    • Timing requirements must be verified.
    • Missed deadlines represent violations of system correctness.

    Other examples¶

    Depending on their design and requirements:

    • Safety-critical industrial robot control functions.
    • Aircraft flight-control functions.
    • Automotive braking-control functions.
    • Certain medical-device control functions.

    Safety-critical systems

    Meeting software deadlines is only one part of functional safety.

    A real safety-related robotic system also requires appropriate risk assessment, hardware design, fault handling, verification and validation.

    A hard real-time deadline alone does not guarantee that a robot is safe.

    1.3.3 Firm real-time systems¶

    A firm real-time requirement allows occasional deadline misses, but a result produced after its deadline is no longer useful (Read more: Difference between hard, firm, & soft) (Read more: Real-Time Embedded Systems, Linköping University).

    Unlike hard real-time requirements, an occasional missed deadline does not necessarily mean the entire system has failed.

    However, the late result may need to be discarded.

    Example: Robot camera processing¶

    Imagine a mobile robot equipped with a camera, the camera produces images periodically, & the robot processes them to detect objects. Now let's suppose the robot receives a new image every 50 ms. And for a particular application, the controller requires an object-detection result before the next image-processing cycle.

    If processing takes too long, the result may refer to an outdated scene.

    For example:

    Image Processing completion Deadline Result
    Frame 1 30 ms 50 ms Useful
    Frame 2 45 ms 50 ms Useful
    Frame 3 70 ms 50 ms Too late
    Frame 4 35 ms 50 ms Useful

    In this example, the result for Frame 3 is considered too late and is discarded by the system. The system continues processing newer frames.

    This illustrates a firm real-time requirement if occasional discarded frames are acceptable under the application's specification.

    Key concept

    In firm real-time systems, occasional deadline misses may be tolerated, but results produced after their deadlines have no value for the intended operation.

    Characteristics¶

    • Occasional missed deadlines may be acceptable.
    • Late results are no longer useful.
    • The system may discard outdated results.
    • Repeated deadline misses may reduce system performance and/or eventually violate other requirements.

    Other examples¶

    Depending on application requirements:

    • Processing camera frames for a robot's current perception cycle.
    • Updating an object-tracking result that becomes obsolete after a defined time.
    • Processing time-sensitive sensor data that must be replaced by newer measurements.

    Note

    A camera-processing task is not automatically firm real-time.

    If its output is needed for a safety-critical function, its timing requirements may be hard real-time.

    If late results remain useful, the requirement may instead be soft real-time.

    1.3.4 Soft real-time systems¶

    A soft real-time requirement is the one in which meeting deadlines is important, but occasional delays are acceptable (Read more).

    A late result may still be useful, although its value/quality may decrease as the delay increases.

    Example: Robot monitoring dashboard¶

    Consider a mobile robot sending its position, battery level, and operating status to a monitoring dashboard. Now if the dashboard is intended to update every 500 ms and an update, may occassionally, arrive after 650 ms.

    The information is slightly delayed, but it may still be useful to the operator.

    The robot can continue operating normally if this delay is permitted by the application requirements.

    This is an example of a soft real-time requirement.

    Characteristics¶

    • Deadlines are desirable but not necessarily strict.
    • Occasional delays may be acceptable.
    • Late results may retain some usefulness.
    • Excessive delays can reduce user experience/performance.

    Other examples¶

    • Displaying robot status information.
    • Updating a noncritical visualisation.
    • Streaming video for general monitoring.
    • Presenting diagnostic information to an operator.

    Key concept

    In soft real-time systems, missed deadlines may reduce performance or quality without necessarily causing system failure.

    1.3.5 Comparing hard, firm and soft real-time requirements¶

    The main difference is the consequence of missing a deadline.

    Characteristic Hard Firm Soft
    Every deadline MUST be met? Yes Not necessarily Not necessarily
    Are occasional misses acceptable? No Sometimes Sometimes
    Is a late result useful? Not acceptable for the specified deadline No May still be useful
    Consequence of a miss System requirement violated Result discarded or obsolete Quality or performance may decrease
    Robotics example Safety-critical control function Time-sensitive perception result Monitoring dashboard

    Important distinction¶

    Hard and firm real-time requirements can both have a sharp deadline after which the result is no longer useful.

    The difference is that:

    • Hard: A missed deadline violates a mandatory system requirement.
    • Firm: An occasional missed deadline is tolerated, but the late result is useless.

    Soft real-time requirements differ because a result may still retain some value after its deadline.

    What does this mean?

    • Hard real-time: Missing a deadline violates a strict timing requirement. The system must be designed to prevent such misses.
    • Firm real-time: A result received after its deadline is no longer useful, although occasional deadline misses may be acceptable.
    • Soft real-time: A late result can still be useful, but the quality of the system's performance may decrease.

    Remember

    The main difference is not necessarily how fast the system operates, but how important it is to meet the deadline and what happens if the deadline is missed!

    Remember

    The classification is determined by the application's timing requirements and the consequences of missing them.

    It is not determined simply by whether the deadline is 1 ms, 10 ms, or 1 second.

    1.3.6 Can one robot contain all three types?¶

    Yes.

    A robotic system may contain several software functions with different timing requirements.

    Consider an autonomous mobile robot operating in a warehouse.

    Function Possible classification Reason
    Safety-critical stop-related control Hard Missing a required deadline violates a critical system requirement
    Object-detection result for the current processing cycle Firm An outdated result may be discarded
    Operator monitoring dashboard Soft Slightly delayed updates may remain useful

    These classifications are illustrative and depend on the actual system design. The same function may have a different classification in another application. For example, object detection used for safety-critical collision prevention may have hard timing requirements, whereas object detection used only for collecting statistics may have soft timing requirements.

    Therefore, engineers should classify individual timing requirements, rather than assuming that an entire robot belongs to one category.

    1.3.7 What determines the correct classification?¶

    When classifying a real-time requirement, consider three questions.

    Question 1: What happens if the deadline is missed?

    Does the missed deadline violate a mandatory system requirement, or can the system tolerate it?

    Question 2: Is the result still useful after the deadline?

    For example, an outdated sensor result may no longer be relevant, while a delayed status message may still be informative.

    Question 3: How frequently can deadlines be missed?

    An application may tolerate an occasional late result but fail to operate acceptably if delays occur repeatedly.

    The answers help determine whether a requirement is hard, firm, or soft.

    Note

    In practice, some systems use more detailed timing models that specify how many deadlines may be missed within a particular sequence of executions.

    These advanced models are beyond the scope of this introductory chapter.

    2.1 From Sequential to Concurrent Programming¶

    2.1.1 Why do robots need to perform multiple activities?¶

    Consider an autonomous mobile robot moving through a laboratory.

    While moving, the robot must perform several activities:

    1. Read its distance sensor.
    2. Calculate the required motor speeds.
    3. Send commands to the motor drivers.
    4. Monitor the battery voltage.
    5. Record diagnostic information.

    Some activities need frequent execution, while others can occur less often.

    For example:

    Activity Example period Frequency
    Motor control 10 ms 100 Hz
    Distance measurement 50 ms 20 Hz
    Battery monitoring 500 ms 2 Hz
    Data logging 1000 ms 1 Hz

    The motor controller may need frequent updates to maintain stable motion, whereas battery monitoring may not require such frequent execution. The challenge is to organise these activities so that each receives sufficient processor time and satisfies its timing requirements.

    A robot does not necessarily need multiple processor cores to handle these activities. Even a single-core processor can manage multiple tasks by switching between them.

    This leads us to the concepts of sequential execution, concurrency, and parallelism.

    2.1.2 Sequential programming¶

    In sequential programming, instructions execute in a defined order within a single flow of execution.

    One operation must finish before the next operation begins.

    For example:

    START
  |
  v
Read distance sensor
  |
  v
Calculate motor command
  |
  v
Send motor command
  |
  v
Record diagnostic data
  |
  v
END

    This is a sequential program.

    The program completes each operation before proceeding to the next.

    C++ example 1: Sequential robot operations¶

    Consider the following C++ program:

    #include <iostream>

void readSensor()
{
    std::cout << "Reading distance sensor\n";
}

void controlMotor()
{
    std::cout << "Calculating motor command\n";
}

void logData()
{
    std::cout << "Recording diagnostic data\n";
}

int main()
{
    readSensor();
    controlMotor();
    logData();

    return 0;
}

    Code explanation¶

    The program contains three functions:

    • readSensor() represents sensor acquisition.
    • controlMotor() represents motor-control calculations.
    • logData() represents diagnostic logging.

    Inside main(), the functions are called sequentially.

    The output is:

    Reading distance sensor
Calculating motor command
Recording diagnostic data

    The execution order is fixed.

    The motor-control function cannot begin until readSensor() has returned.

    Similarly, logData() cannot begin until controlMotor() has returned.

    Is sequential programming bad?¶

    No.

    Sequential programming is often the simplest & most appropriate/optimal solution for small applications. E.g., a robot that performs one short sensor reading, one calculation & one motor update in a predictable cycle may work well using a sequential program.

    However, problems can arise when operations have different execution times or timing requirements.

    Execution time in a sequential program¶

    From the above example, let's suppose the those three operations take:

    Operation Execution time
    Read sensor 8 ms
    Calculate motor command 4 ms
    Record data 12 ms

    Assuming the operations execute continuously without interruption and that other overheads are negligible/ignored.

    The total execution time is:

    \[ C_{\text{total}} = C_{\text{sensor}} + C_{\text{control}} + C_{\text{logging}} \]

    Substituting the values:

    \[ C_{\text{total}} = 8 + 4 + 12 \]
    \[ \boxed{C_{\text{total}} = 24\ \text{ms}} \]

    If the program repeats these operations continuously, one complete cycle requires at least 24 ms under these assumptions.

    What if motor control requires a 10 ms period?¶

    Suppose the motor controller must execute every 10 ms. A sequential program that performs all three operations once per cycle can't meet that period if the operations require 24 ms in total.

    Even though the motor-control calculation itself requires only 4 ms, the other operations delay its next execution.

    This is an important distinction:

    A task's timing behaviour depends not only on its own execution time, but also on how other activities are organised.

    Real execution times may vary.

    C++ example: Simulating sequential task durations¶

    We can use C++ to simulate the time taken by different robot operations.

    Create a file named:

    sequential_robot.cpp

    #include <iostream>
#include <chrono>
#include <thread>

void readSensor()
{
    std::cout << "Reading sensor...\n";

    std::this_thread::sleep_for(
        std::chrono::milliseconds(8)
    );
}

void controlMotor()
{
    std::cout << "Calculating motor command...\n";

    std::this_thread::sleep_for(
        std::chrono::milliseconds(4)
    );
}

void logData()
{
    std::cout << "Logging data...\n";

    std::this_thread::sleep_for(
        std::chrono::milliseconds(12)
    );
}

int main()
{
    using Clock = std::chrono::steady_clock;

    auto start = Clock::now();

    readSensor();
    controlMotor();
    logData();

    auto finish = Clock::now();

    double elapsed_ms =
        std::chrono::duration<double, std::milli>(
            finish - start
        ).count();

    std::cout << "Total elapsed time: "
              << elapsed_ms << " ms\n";

    return 0;
}

    Compile and execute¶

    Using a C++17-compatible GCC compiler:

    g++ -std=c++17 -O0 sequential_robot.cpp -o sequential_robot

    On Windows PowerShell:

    .\sequential_robot.exe

    On Linux or macOS:

    ./sequential_robot

    Expected behaviour¶

    The program prints messages in the same order as the function calls.

    The total elapsed time will normally be approximately 24 ms or longer.

    However, the measured duration may vary because of:

    • Operating-system scheduling,
    • Thread wake-up delays,
    • Console output,
    • Other system activities.

    Important measurement distinction

    std::this_thread::sleep_for() suspends the current thread.

    It does not perform CPU-intensive calculations for the requested duration.

    Therefore, this example simulates elapsed operation durations, not actual CPU execution times.

    The example is intended to demonstrate sequential waiting and timing, not to measure processor workload.

    Try it yourself¶

    Modify the program so that:

    1. Sensor acquisition takes 5 ms.
    2. Motor control takes 3 ms.
    3. Logging takes 20 ms.

    Before running the program, calculate the expected total delay. Run the program five times. Does the measured elapsed time equal exactly 28 ms?

    Explain any differences.

    2.1.3 What is concurrency?¶

    Concurrency means that multiple activities can make progress during overlapping periods of time.

    The activities do not necessarily execute at precisely the same instant.

    For example, consider a single-core processor running:

    • Task A: Sensor processing.
    • Task B: Motor control.
    • Task C: Data logging.

    The processor might execute a short portion of Task A, switch to Task B, then execute Task C before returning to Task A.

    Only one task executes on the processor core at a particular instant, but all three tasks make progress over time.

    This is called concurrent execution.

    Example: A robot performing multiple activities¶

    A mobile robot may need to continue controlling its motors while periodically receiving sensor measurements.

    Instead of executing all activities in one long sequential cycle, the program can organise them as separate tasks.

    The operating system can then schedule the tasks according to its scheduling policy.

    Time  -------------------------------------------------->

CPU    | Sensor | Motor | Logger | Motor | Sensor | Motor |
    Figure 2.1.2: Concurrent execution on a single-core processor

    The processor executes one task at a time, but switches between tasks.

    The tasks are concurrent because their execution progresses over overlapping periods.

    Important

    Concurrency does not automatically mean that the program runs faster.

    Its main benefit is allowing multiple activities to be organised and scheduled independently.

    Whether timing performance improves depends on the task design, scheduling policy and hardware. FreeRTOS. RTOS Fundamentals and Task Scheduling. (Read more: RTOS Fundamentals)

    2.1.4 Concurrency versus parallelism¶

    The terms concurrency and parallelism are related but describe different concepts.

    Concurrency¶

    Multiple activities make progress over overlapping periods.

    On a single-core processor, this can happen through task switching.

    Parallelism¶

    Multiple activities execute simultaneously on different processing resources.

    For example, a processor with multiple cores may execute sensor processing on one core and motor control on another at the same instant.

    Example¶

    Suppose a robot has two software tasks:

    • Task A processes sensor measurements.
    • Task B calculates motor commands.

    On a single-core processor, the operating system may alternate between the tasks.

    On a multicore processor, the tasks may execute simultaneously if the scheduler places them on different cores.

    Comparison¶

    Characteristic Concurrency Parallelism
    Multiple activities can make progress Yes Yes
    Simultaneous execution required No Yes
    Possible on a single-core processor Yes Not for two CPU-executing threads simultaneously on the same core
    Multiple processor cores required No Multiple execution resources are needed for simultaneous CPU execution
    Main idea Managing overlapping activities Executing activities simultaneously

    Remember

    Concurrency is about organising multiple activities.

    Parallelism is about executing multiple activities at the same time.

    A program can be concurrent without being parallel.

    Reference: [2].

    2.1.5 What is a software task?¶

    In robotics, a task is a logical unit of work that performs a particular function.

    Examples include:

    • Reading a distance sensor.
    • Updating a motor controller.
    • Monitoring battery voltage.
    • Processing camera measurements.
    • Recording diagnostic information.

    A task may execute:

    • Periodically.
    • In response to an event.
    • Once when requested.

    The word task is used somewhat differently across programming environments.

    In real-time operating systems such as FreeRTOS, a task is a schedulable execution entity managed by the RTOS.

    In general-purpose C++ programming, we can organise logical tasks using functions and execute them through threads.

    Task versus thread¶

    A task describes the work that needs to be performed.

    A thread is an execution mechanism that allows a sequence of instructions to run independently within a process.

    For example:

    void sensorTask()
{
    // Read and process sensor data.
}

    This function represents a logical sensor task.

    However, simply defining the function does not create a separate thread.

    Calling it normally:

    sensorTask();

    executes it in the calling thread.

    Later, we can create a separate thread using:

    std::thread sensorThread(sensorTask);

    The sensorTask() function can then execute in the newly created thread.

    Note

    In C++, std::thread is available from C++11 onwards.

    It allows programrs to create separate threads of execution within a process (Read more: std::thread — C++ Reference.).

    2.1.6 Periodic and event-driven tasks¶

    Robotic software commonly contains both periodic and event-driven activities.

    Periodic tasks¶

    A periodic task is intended to execute repeatedly at regular intervals.

    Examples:

    • Read an encoder every 10 ms.
    • Update motor commands every 20 ms.
    • Monitor battery voltage every 500 ms.

    The task period is represented by:

    \[ T \]

    Its frequency is:

    \[ f = \frac{1}{T} \]

    For example:

    \[ T = 20\ \text{ms} = 0.020\ \text{s} \]
    \[ f = \frac{1}{0.020} \]
    \[ \boxed{f = 50\ \text{Hz}} \]

    Event-driven tasks¶

    An event-driven task executes when a particular event occurs.

    Examples:

    • A user presses an emergency-stop button.
    • A new message arrives.
    • A sensor reports that data is available.
    • A communication timeout occurs.

    Unlike a periodic task, an event-driven task does not necessarily execute at fixed intervals.

    Which approach is better?¶

    Neither is universally better. Periodic execution is useful when regular updates are required. Event-driven execution is useful when processing should occur in response to specific events. Many robotic systems use a combination of both. E.g., a motor controller may update periodically, while a communication task waits for incoming commands.

    FreeRTOS provides task scheduling and blocking mechanisms that support these types of applications.

    Warning

    An event-driven design does not automatically provide immediate response.

    The event must still be detected and the corresponding task scheduled.

    2.1.7 Why not simply use one large loop?¶

    A beginner might organise all robot activities inside a single while loop.

    For example:

    while (true)
{
    readSensor();
    controlMotor();
    checkBattery();
    logData();
}

    This approach is easy to understand.

    However, it has several limitations.

    Limitation 1: Every operation delays the next¶

    If logData() takes a long time, the next sensor reading and motor-control calculation are delayed.

    Limitation 2: Different periods are difficult to manage¶

    Motor control may need to run every 10 ms, while battery monitoring may only be needed every 500 ms.

    Calling every function once per loop does not naturally satisfy these different timing requirements.

    Limitation 3: Blocking operations can delay the entire loop¶

    Suppose readSensor() waits for a sensor response.

    While it is waiting, the other functions cannot execute in that same thread.

    Limitation 4: Timing requirements become harder to analyse¶

    When many activities share one sequential execution path, a delay in one operation affects the timing of the others.

    However, it doesn't automatically mean one loop is always unsuitable. A carefully designed single-loop program can be suitable for simple embedded systems. E.g., a cooperative scheduler can use a single loop to execute short operations when their scheduled times arrive.

    The important requirement is that operations must not block or execute unpredictably for too long. For more complex applications, separating activities into independently scheduled tasks can make the design easier to organise.

    C++ example: A simple cooperative task loop¶

    Before introducing multiple threads, we can improve a sequential program by giving different operations their own intended periods.

    This example uses a single thread (not multithreaded programming).

    Create a file named:

    cooperative_robot.cpp

    #include <iostream>
#include <chrono>
#include <thread>

int main()
{
    using Clock = std::chrono::steady_clock;

    const auto sensor_period =
        std::chrono::milliseconds(50);

    const auto motor_period =
        std::chrono::milliseconds(20);

    auto now = Clock::now();

    auto next_sensor = now;
    auto next_motor = now;

    const auto end_time =
        now + std::chrono::seconds(1);

    while (Clock::now() < end_time)
    {
        now = Clock::now();

        if (now >= next_sensor)
        {
            std::cout << "Sensor update\n";

            next_sensor += sensor_period;
        }

        now = Clock::now();

        if (now >= next_motor)
        {
            std::cout << "Motor update\n";

            next_motor += motor_period;
        }

        std::this_thread::sleep_for(
            std::chrono::milliseconds(1)
        );
    }

    return 0;
}

    The program contains two logical activities:

    1. Sensor update every 50 ms.
    2. Motor update every 20 ms.

    The variable: next_sensor stores the intended time of the next sensor update.

    Similarly next_motor stores the intended time of the next motor update.

    The conditions if (now >= next_sensor) and if (now >= next_motor) check whether the corresponding activity is due.

    After an activity is executed, its next scheduled time is advanced by one period.

    Why is this useful?¶

    The program does not need to call every function on every iteration. Each logical activity has its own intended period. This is a basic form of cooperative, time-triggered task organisation.

    Important limitations¶

    The program still uses only one thread.

    Therefore:

    • A long sensor operation can delay the motor update.
    • Both activities cannot execute simultaneously.
    • The operating system may delay the loop.
    • The 1 ms sleep can introduce additional timing variation.
    • If the program falls behind schedule, overdue activities may execute in successive loop iterations.

    The program is deliberately simple and does not implement a complete overrun-handling policy.

    2.1.8 Choosing between sequential and concurrent programming¶

    Concurrency is useful when an application contains activities with different timing requirements or operations that may block independently. However, concurrency introduces additional complexity. E.g., multiple threads may need to access the same sensor data. If they access shared data without appropriate coordination, incorrect or inconsistent results may occur.

    These problems are called race conditions and will be studied in later chapters.

    Practical decision guide¶

    flowchart TD
    A["Identify robot software activities"] --> B{"Can a simple sequential design meet the requirements?"}
    B -->|"Yes"| C["Use a simple sequential design"]
    B -->|"No"| D{"Can short non-blocking operations be scheduled cooperatively?"}
    D -->|"Yes"| E["Consider a cooperative task loop"]
    D -->|"No"| F["Consider independently scheduled threads or RTOS tasks"]
    C --> G["Measure and verify timing"]
    E --> G
    F --> H["Design safe communication and synchronisation"]
    H --> G

    The choice should be based on measured timing requirements, system complexity and hardware capabilities.

    Do not introduce concurrency merely because it is available.

    2.1.9 Example: Selecting an approach for a robot¶

    A small robot performs the following activities:

    Activity Period Typical processing duration
    Read distance sensor 50 ms 5 ms
    Calculate motor command 20 ms 3 ms
    Record diagnostic data 500 ms 15 ms

    Suppose all three functions are executed sequentially in one repeated cycle.

    The combined processing duration is:

    \[ C_{\text{total}} = 5 + 3 + 15 \]
    \[ \boxed{C_{\text{total}} = 23\ \text{ms}} \]

    If every activity executes once per cycle, the motor-control function cannot achieve a 20 ms start-to-start period in this design.

    Possible improvement 1: Cooperative scheduling¶

    Execute the functions only when their intended periods are reached.

    This may be sufficient if:

    • All operations are short.
    • Operations do not block unpredictably.
    • The resulting timing measurements satisfy the requirements.

    Possible improvement 2: Separate threads¶

    Use independently scheduled threads for:

    • Sensor acquisition.
    • Motor control.
    • Logging.

    This allows the operating system to schedule the activities separately.

    However, shared data must be handled safely.

    Which solution should we choose?¶

    There is not enough information to guarantee that either approach will satisfy every deadline.

    We would need to know:

    • Worst-case execution times.
    • Deadlines.
    • Blocking behaviour.
    • Scheduling policy.
    • Hardware and operating-system characteristics.

    The appropriate engineering approach is to implement a suitable design, measure its behaviour, and assess whether the timing requirements are satisfied. For strict timing guarantees, additional analysis, and validation may be required.
